Repo Agent architecture

Every component in the demo and the three flows between them: indexing the repositories, answering a developer in the IDE, and monitoring usage. Badges on the diagram match the numbered steps below.

IDE request flow (R) Indexing flow (I) Telemetry and monitoring flow (M) Response / return path

Indexing

Runs in ingest on start-up and every INGEST_INTERVAL_SECONDS.

  1. I1
    Read repositories. GitLab REST API with a read-only token (or local folders for the sample repos). Repos and their access_scope come from config/sources.yaml.
  2. I2
    Read standards. The approved coding standard, split into one chunk per clause with version and section path.
  3. I3
    Embed changed files only. Unchanged fingerprints are skipped; new chunks go to Voyage voyage-code-3 in batches.
  4. I4
    Write to Atlas. Chunks with embeddings, file content and fingerprints, the run record. Creates chunks_vector and chunks_text if missing.

IDE request

One developer question in Continue, end to end.

  1. R1
    Ask. Continue sends the conversation, open file and selection to /v1/chat/completions with the developer's token.
  2. R2
    Embed the question. Voyage, input_type=query.
  3. R3
    Search Atlas. $vectorSearch and $search in parallel, both pre-filtered to the developer's scopes, then fused.
  4. R4
    Rerank. Voyage rerank-2.5 orders the candidates; top-k code plus standard clauses are kept.
  5. R5
    Call OpenAI. Grounded prompt with labelled sources [S1…] and rules; tool calls pass through.
  6. R6
    Stream back. Answer with [S# path:lines] citations and a Sources list.
  7. R7
    Review and apply. The developer accepts the diff; Continue merges it via repo-agent-apply. The agent never writes to a repo.
  8. R8
    Agent-mode tools. search_code, search_standards, get_file, list_repos over /mcp, same permissions.

Telemetry and monitoring

What the console shows and where it comes from.

  1. M1
    Outcomes from the IDE. Continue's dev-data export posts accept / reject and feedback events, with level: noCode.
  2. M2
    Usage events. Every request writes latency per stage, tokens, cost, sources, citations and permission-hidden counts. The rollup job aggregates them hourly.
  3. M3
    Open the console. An admin signs in to web-ui on port 8080 with an admin token.
  4. M4
    Read metrics. nginx proxies /api to /admin/*, which reads rollups, events, outcomes, eval runs and the audit log.
